## A. 可以直接继续执行的低风险任务

这些任务不删除数据、不合并数据、不修改真实记忆内容，可直接做。

### A1. Memory Quality Review 只读页面

目标：让用户在 Dashboard 里看到 99 条 source-aware memory 的质量状态。

功能：

- 列表展示 source-aware memory；
- 筛选：
  - 全部；
  - 疑似临时任务；
  - 疑似重复；
  - 缺标题来源；
  - evidence 数不足；
- 点击查看 evidence trace；
- 只读展示，不提供删除/合并按钮。

价值：先让用户能判断哪些 memory 值得保留。

### A2. Memory Quality Audit API

目标：把当前 `reports/audit_source_aware_quality.py` 的规则产品化为 API。

建议接口：

```text
GET /api/source-aware/memory-quality
```

返回：

- counts；
- pollution flags；
- temporary-task flags；
- duplicate groups；
- missing title groups；
- samples。

### A3. Source Session 详情分页

当前详情页前端可选择前 80/150/300，但后端仍一次返回固定 turns。后续应改为后端分页。

建议接口：

```text
GET /api/source-aware/session/:id/turns?page=1&page_size=100&filter=human_final|tool_process|all
```

价值：后续全量导入 HanaAgent 后避免详情页变慢。

### A4. 导入前质量 dry-run 报告增强

目标：在正式 extraction 前，dry-run 就提示：

- 预计 memory 数；
- 疑似临时任务数；
- 疑似系统污染数；
- 缺标题会话数；
- 重复候选数。

这样正式写库前可以提前发现风险。

### A5. 文档补全

需要把以下文档补齐：

## B. 可以实现，但真实写库前需要用户确认的任务

这些任务会改变真实主库结构或数据，不能静默执行。

### B1. 增加 memory review 状态字段

建议新增字段或表：

```text
memory_units.review_status: pending / accepted / rejected / merged / archived
memory_units.retention_class: long_term / project_state / temporary_task / noise
memory_units.quality_flags_json
memory_units.reviewed_at
memory_units.reviewed_by
```

或者新表：

```text
memory_reviews(memory_id, review_status, retention_class, quality_flags_json, note, created_at, updated_at)
```

倾向新表，因为不侵入核心 memory 表。

### B2. Review 操作 API

建议接口：

```text
POST /api/source-aware/memory/:id/review
```

动作：

- 标记保留；
- 标记临时任务；
- 标记噪声；
- 标记待合并；
- 添加人工备注。

这一步会写真实库，需要确认。

### B3. 重复 memory 合并机制

目标：不是删除重复，而是形成一个 canonical memory，多条 evidence 合并到同一条下。

建议原则：

- 先只生成 merge candidates；
- 人工确认后再 merge；
- merge 前备份；
- 被合并 memory 不物理删除，只标记 `merged` / `superseded_by`。

### B4. 临时任务降权/归档

当前有 20 条疑似临时任务。处理方式不能直接删除，建议：

- 标记 `retention_class = temporary_task`；
- 默认不进入长期 recall；
- 仍保留 evidence trace；
- 可在审计页面查看。

### B5. Missing Title 人工确认

目标：改善可读性，但不污染 `original_title`。

规则：

- `original_title` 永远只存 Agent 原始标题；
- 人工确认标题只写 `display_title`；
- `display_title_source = human_confirmed`；
- `title_source` 仍保持 `missing`。

## C. 后续能力建设任务

这些是 V0.9 后半段到 V1 的核心。

### C1. 智能结构化 memory extraction

当前抽取是保守的 user-turn 摘要，后续要升级成：

```text
用户任务 + assistant final answer + evidence turns
→ title / summary / memory_type / tags / importance / retention_class
```

必须先有 Review 机制，再做批量智能抽取。

### C2. 多来源全量导入

顺序建议：

1. HanaAgent limit 10 已完成；
2. HanaAgent limit 50 dry-run；
3. HanaAgent limit 50 source-only；
4. HanaAgent limit 50 extraction；
5. Codex source-only；
6. Codex conservative extraction；
7. WorkBuddy 暂时保持 source-only；
8. Qoder 等产生测试会话后再适配。

### C3. Source-aware recall 接入

目标：长期记忆检索返回时带 evidence：

```text
memory
→ source_session
→ source_turns
→ 原始会话归属
```

### C4. Hebbian / 图谱重接

新图谱不能基于旧 memory_units 盲目建图，必须基于 review 后的 canonical memory。

建议顺序：

1. accepted long_term memory；
2. project_state memory；
3. evidence-backed relation；
4. graph edge 权重；
5. Space-aware 扩散。

### C5. Persona / Todo 重接

Persona 和 Todo 不应直接从 source turns 抽，而应从已审核 memory 派生：

```text
source_turns → memory_units → reviewed/canonical memory → persona/todo
```

## D. 当前优先级建议

最推荐执行顺序：

```text
1. A2 Memory Quality Audit API
2. A1 Memory Quality Review 只读页面
3. B1 review 状态表 migration（确认后）
4. B2 Review 操作 API/UI（确认后）
5. B3 duplicate candidates，只生成候选不合并
6. B4 临时任务降权/归档（确认后）
7. HanaAgent limit 50 dry-run
8. 再决定是否扩大导入
```

原则：

- 先看清质量，再扩大导入；
- 先只读候选，再写库标记；
- 先标记归档，不物理删除；
- 任何真实库变更前：停服务、checkpoint、备份、确认。
